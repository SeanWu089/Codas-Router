# Qualified Windows stable artifact workflow

Retained on a separate engineering branch so the tested candidate commit is unaffected.
The workflow has not been run. No qualification report or passing observations
have been generated by this preparation.

The final stable workflow is **not enabled in `.github/workflows`**.
Saving this engineering template on a separate branch does not constitute
physical-PC acceptance or stable publication. Actual Windows usage-scenario
acceptance and its genuine report are still required before enabling the
qualified-release trigger.

## Integration after actual acceptance

1. Start `release/windows-qualified-20261123` from the exact engineering commit
   whose complete candidate workflow succeeded and whose package was tested on
   Windows. This branch name does not match `release/windows-stable-*`.
2. Copy `engineering/windows-qualification/windows-qualified-artifact.yml.example` into
   `.github/workflows/windows-qualified-artifact.yml` on that separate branch.
3. Add the genuine, sanitized report at
   `releases/windows-0.2.0-qualification.json`. It must satisfy the existing
   `windows-daily-use` contract documented in `dependencies/README.md`, including
   all actual physical-Windows gates and the exact candidate source, installer
   and payload hashes. Do not copy fixture observations into this report.
4. The report needs two additional provenance fields:
   `testedEngineeringRevision` is the full lowercase SHA of the engineering
   candidate commit, not the older frozen transport commit;
   `validatedCIRunId` is the positive numeric ID of its successful
   `windows-stable-validation.yml` run. `validatedCIRunAttempt` may additionally
   pin the successful attempt; if present it must match GitHub's current result.
5. Stable wording may be updated in `README-WINDOWS.md` after acceptance. The
   workflow refuses changes to product code, dependencies, builder, installer,
   runtime, license, tests, or candidate CI compared with the tested engineering
   revision. A fix to any of these requires a newly tested candidate revision.
6. Review and commit the workflow, real report and truthful documentation on
   this qualified branch. Pushing it is the intentional workflow trigger.
   Preparation alone does not trigger anything.

The report remains a record of actual Windows acceptance. GitHub CI verifies
its schema, exact package bytes and relationship to a successful prior CI run;
it does not replace or repeat the physical Windows scenarios. The evidence
inventory in the report must reference genuine retained evidence. This workflow
does not fetch private raw acceptance records or create evidence for them.
Only sanitized report metadata is included in the artifact.

There is no minimum cumulative duration. Natural wake and full-PC reboot may
remain explicitly unobserved/untested under the authorized daily-use policy.
Known failed observations are rejected by the existing builder gate.

## Checks performed before building

- After the full-history checkout and pinned Node setup, the workflow invokes
  `scripts/windows/stable/restore-frozen-source.mjs` before qualification/build
  code needs `git show c1497ca...`. It verifies the checked-in bundle and its
  provenance pins, then imports only the original transport objects into the
  fixed `refs/codas/frozen-windows-transport` ref. It does not fetch remote
  source, change the checked-out source, or reconstruct the original commits.
  Full checkout is still necessary for the bundle's prerequisite commit.
- The report passes the existing builder's daily-use qualification validator.
- `testedEngineeringRevision` is an ancestor of the immutable current checkout.
- Product, dependency, builder and validation paths have no differences from
  the tested revision; tracked checkout files remain unmodified.
- Read-only GitHub API requests confirm that `validatedCIRunId` belongs to the
  same repository and exact tested SHA, has completed successfully, originated
  from a candidate release branch, and belongs to the expected workflow.
- Both Windows Node 22/24 jobs, complete candidate packaging and candidate
  draft attachment jobs must be present and successful in the latest attempt.
  An incomplete or unexpected job inventory fails closed. If an earlier CI
  attempt was only partly rerun and GitHub does not return all required jobs,
  a complete successful candidate attempt is needed; the workflow will not
  infer missing results.
- The referenced CI run is reread to reject an overlapping rerun.

The build uses Node 22.23.3, fetches only exact upstream archives through
`--prepare-dependencies --official-only`, then invokes `--stable --offline`
with `--version windows-0.2.0` and the real report. The builder rechecks all
payload and installer/bootstrap hashes against that report and independently
verifies its compact archive before assembly succeeds.

## Artifact and permissions

The workflow grants only `contents: read` and `actions: read`. The only GitHub
REST requests in its code are GET requests. The upload action writes an Actions
artifact; the workflow has no release creation, release asset upload, release
publication, Git ref update or `contents: write` capability.

The artifact is named
`Codas-Windows-0.2.0-<qualified-commit-sha>-<run-attempt>` and contains exactly:

- `Codas-Windows-0.2.0.zip`
- `release.json`
- `payload-manifest.json`
- `qualification.json`
- `stable-build.json`
- `SHA256SUMS`

`stable-build.json` records both the qualified source commit and the tested
engineering commit, successful prior CI run/attempt and required jobs, source
report and packaged report hashes, exact manifest digest, build toolchain,
ZIP size/hash and current build run. The ZIP uses sorted short outer paths,
fixed file modes and the qualified commit timestamp. It rejects symbolic links,
unexpected long outer paths and an unpacked dependency tree; it checks the ZIP
roundtrip and the exact metadata bytes inside it. The payload remains in the
compact Node-extracted archive. Nothing is publicly released by this workflow.

## Authenticated download on the Mac

After the qualified workflow succeeds, use the existing authenticated `gh`
session directly on the Mac. The values below are placeholders to replace
with the actual repository, successful stable run and displayed artifact name.

```sh
codas_repo='OWNER/REPO'
codas_stable_run='ACTUAL_SUCCESSFUL_RUN_ID'
codas_artifact_name='EXACT_ARTIFACT_NAME_FROM_THE_SUCCESSFUL_RUN'
codas_release_dir="$(mktemp -d /tmp/codas-windows-stable.XXXXXX)"

gh api "repos/$codas_repo/actions/runs/$codas_stable_run" \
  --jq '{status, conclusion, head_sha, run_attempt}'
gh run download "$codas_stable_run" --repo "$codas_repo" \
  --name "$codas_artifact_name" --dir "$codas_release_dir"

cd "$codas_release_dir"
shasum -a 256 -c SHA256SUMS
```

Check the downloaded `stable-build.json`, `release.json` and actual qualification
before the separately authorized stable release step. Create/upload/publish
through the Mac's authenticated `gh` session using the exact verified source
commit and files. Do not overwrite an unrelated release or conflicting asset.
No large base64 transfer through Codas or additional CI release helper is needed.
